\# 2. SLO Хүснэгт



| Сценарио | SLI | Босго | Цонх |

|-----------|-----------|-----------|-----------|

| Performance | /cart/add latency | p95 < 50 ms | 20 VU, 1 минут |

| Reliability | /pay error rate | < 8% | 20 VU, 1 минут |

| Availability | Checks success rate | > 90% | 20 VU, 2 минут |



\## Босго сонгосон үндэслэл



\- `/cart/add` endpoint локал орчинд маш хурдан ажилладаг тул p95 < 50 ms гэсэн босго сонгосон.

\- `/pay` endpoint нь зориудаар ойролцоогоор 5%-ийн алдаа үүсгэдэг тул error rate < 8% гэсэн бодитой босго сонгосон.

\- Availability-д 90%-ийн босго ашигласан бөгөөд богино хугацааны алдааг зөвшөөрсөн.



\---



\# Error Budget



\*\*Availability SLO:\*\* 90%



\*\*Тестийн хугацаа:\*\* 120 секунд



\*\*Error Budget тооцоо\*\*



```text

120 × 10%

= 12 секунд

```



Иймээс 2 минутын хугацаанд хамгийн ихдээ 12 секундийн доголдлыг зөвшөөрөх боломжтой.

\# 3. PASS Туршилтын Үр Дүн



\## Thresholds



\- checks > 90%

\- cart p95 < 50 ms

\- report p95 < 450 ms

\- pay error rate < 8%



\## Хэмжилтийн үр дүн



| Үзүүлэлт | Үр дүн |

|-----------|-----------|

| Availability | 98.55% |

| /cart/add p95 | 544.16 µs |

| /report p95 | 397.50 ms |

| /pay error rate | 4.33% |



Бүх threshold амжилттай PASS болсон.



\---



\# 4. Chaos Туршилт



Тест ажиллаж байх үед серверийг Ctrl+C ашиглан зогсоож, 10 секундийн дараа дахин ажиллуулсан.



Туршилтын үеэр дараах төрлийн алдаанууд бүртгэгдсэн.



```text

connection refused

```



Энэ нь сервер унасан хугацаанд хүсэлтүүд боловсруулагдаагүй болохыг харуулсан.



\## Chaos Туршилтын Үр Дүн



| Үзүүлэлт | Үр дүн |

|-----------|-----------|

| Availability | 81.21% |

| Reliability (/pay error rate) | 21.93% |

| Failed Requests | 18.78% |



\## Тайлбар



Chaos туршилтын үеэр Availability threshold (>90%) хангагдаагүй тул FAIL болсон.



Reliability threshold (<8%) мөн FAIL болсон. Сервер унах үед `/pay` endpoint рүү очсон хүсэлтүүд бүгд алдаа үүсгэж байсан учир error rate огцом өссөн.



Сервер унасан хугацаанд connection refused алдаа шууд буцаж байсан тул хүсэлтээр тооцсон availability үзүүлэлт хугацаагаар тооцсон error budget-аас илүү муудсан.



Availability нь систем ажиллаж байгаа эсэхийг хэмждэг бол Reliability нь зөв үр дүн буцааж байгаа эсэхийг хэмждэг. Нэг эвдрэл хоёр SLO-г зэрэг зөрчиж байгааг ажигласан.



\---



\# 5. FAIL Туршилт



FAIL хувилбарт дараах threshold ашигласан.



```javascript

'http\_req\_duration{name:report}': \['p(95)<100']

```



\## Үр Дүн



| Үзүүлэлт | Үр дүн |

|-----------|-----------|

| /report p95 | 398.35 ms |

| Threshold | p95 < 100 ms |

| Үр дүн | FAIL |



k6 дараах алдааг гаргасан.



```text

thresholds on metrics 'http\_req\_duration{name:report}' have been crossed

```



Exit code:



```text

99

```



Энэ нь CI/CD pipeline дээр threshold зөрчигдвөл build автоматаар зогсох боломжтойг харуулж байна.

\# 6. Дүгнэлт



Энэхүү лабораторийн ажлаар чанарын сценариог SLO болон k6 threshold болгон хувиргах үйл явцыг практик дээр хэрэгжүүллээ. Performance, Reliability болон Availability гэсэн гурван төрлийн сценарио боловсруулсан. Сценарио бүрээс тохирох SLI тодорхойлж босго утгууд сонгосон. Performance туршилтын үед `/cart/add` endpoint маш хурдан ажиллаж, тогтоосон p95 latency босгыг хангаж чадсан. Reliability туршилтын үед `/pay` endpoint-ийн алдааны хувь 8%-иас бага байсан тул SLO хангагдсан. Availability туршилтын үед систем хэвийн нөхцөлд 98%-иас дээш амжилтын хувьтай ажилласан. Chaos туршилтаар серверийг зориудаар унтраахад Availability болон Reliability үзүүлэлтүүд мэдэгдэхүйц буурсан. Үүний үр дүнд хоёр threshold зэрэг FAIL болсон. Error budget ойлголтыг бодит туршилтаар шалгаж, хугацаагаар болон хүсэлтээр хэмжихэд ялгаа гарч байгааг ажигласан. Энэхүү лаборатори нь чанарын сценарио, SLO болон автомат threshold шалгалтын хоорондын уялдаа холбоог бодитоор ойлгоход тусаллаа.
