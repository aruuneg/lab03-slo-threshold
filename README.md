## 2. SLO хүснэгт

| Сценарио | SLI | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | `/cart/add` latency | p95 < 50 ms | 20 VU, 1 минут |
| Reliability | `/pay` error rate | < 8% | 20 VU, 1 минут |
| Availability | Checks success rate | > 90% | 2 минут, 10 секундийн зогсолт |
| Report performance | `/report` latency | p95 < 450 ms | 20 VU, 1 минут |

### Босго сонгосон үндэслэл

- `/cart/add` нь локал орчинд ажилладаг хурдан endpoint тул p95 < 50 ms гэсэн босгыг сонгосон.
- `/pay` endpoint нь зориудаар ойролцоогоор 5% алдаа үүсгэдэг тул error rate < 8% гэсэн босго нь бодит нөхцөлд тохиромжтой.
- Availability SLO-г 90% гэж сонгосон бөгөөд богино хугацааны доголдлыг зөвшөөрөх боломжтой гэж үзсэн.
- `/report` endpoint нь зориудаар 200–400 ms сааталтай учир p95 < 450 ms гэсэн босго сонгосон.

## 3. Error Budget

Availability SLO:

```text
90%
```

Тестийн хугацаа:

```text
2 минут = 120 секунд
```

Availability-ийн зөвшөөрөгдөх алдаа:

```text
100% - 90% = 10%
```

Error budget:

```text
120 секунд × 10% = 12 секунд
```

Иймээс 2 минутын хугацаанд цаг хугацаагаар тооцвол хамгийн ихдээ **12 секундийн доголдол** зөвшөөрөгдөнө.

Chaos туршилтаар серверийг 10 секунд орчим зогсоосон боловч хүсэлтээр хэмжсэн availability 90%-иас доош гарсан. Үүний шалтгаан нь сервер ажиллахгүй байх үед хүсэлтүүд `connection refused` алдаагаар маш хурдан буцаж, богино хугацаанд олон амжилтгүй хүсэлт бүртгэгдсэнтэй холбоотой. Иймээс цагаар тооцсон error budget болон хүсэлтийн тоогоор тооцсон availability нь ижил үр дүн өгөхгүй байж болохыг туршилтаар ажигласан.

## 4. PASS туршилтын үр дүн

PASS туршилтад дараах threshold-уудыг ашигласан:


| Үзүүлэлт | Threshold | Бодит утга | Үр дүн |
|---|---:|---:|---|
| Availability / checks | > 90% | 98.67% | PASS |

| `/report` p95 | < 450 ms | 392.72 ms | PASS |
| `/pay` error rate | < 8% | 3.97% | PASS |

PASS туршилтын үед бүх threshold амжилттай хангагдсан.

`/cart/add` endpoint-ийн p95 нь 696.71 µs байсан бөгөөд 50 ms-ийн босгоос маш бага байна. `/report` endpoint-ийн p95 нь 392.72 ms байсан тул 450 ms-ийн босгыг хангаж байна. `/pay` endpoint-ийн error rate 3.97% байсан бөгөөд 8%-ийн reliability SLO-г хангасан. Checks success rate 98.67% байсан тул availability threshold мөн PASS болсон.

## 5. Chaos туршилтын үр дүн

Chaos туршилтыг 2 минутын хугацаанд ажиллуулсан. Туршилтын явцад локал серверийг зориудаар зогсоож, ойролцоогоор 10 секундийн дараа дахин ажиллуулсан.

Сервер зогссон үед k6 дараах төрлийн алдааг бүртгэсэн:

```text
No connection could be made because the target machine actively refused it.
```

### Бодит хэмжилтийн үр дүн

| Үзүүлэлт | Threshold | Бодит утга | Үр дүн |
|---|---:|---:|---|
| Availability / checks | > 90% | 81.21% | FAIL |
| `/cart/add` p95 | < 50 ms | 534.14 µs | PASS |
| `/report` p95 | < 450 ms | 396.10 ms | PASS |
| `/pay` error rate | < 8% | 21.93% | FAIL |
| Failed checks |  | 18.78% |  |

Chaos туршилтын үед checks success rate **81.21%** болж availability threshold болох 90%-ийг хангаж чадаагүй.

`/pay` endpoint-ийн error rate **21.93%** болж reliability threshold болох 8%-ийг мөн давсан. Энэ нь сервер унасан үед `/pay` хүсэлтүүд connection error-оор амжилтгүй болж, зөвхөн endpoint-д зориудаар суулгасан 5%-ийн алдаа биш системийн availability доголдол reliability хэмжүүрт мөн нөлөөлснийг харуулсан.

Chaos тестийн үед нийт checks-ийн **18.78%** буюу 1084 хүсэлт амжилтгүй болсон.

Availability болон reliability SLI-г илүү сайн тусгаарлахын тулд availability-д серверийн health/status endpoint-ийн амжилтыг тусад нь хэмжиж, `/pay` reliability-д зөвхөн сервер ажиллаж байх үеийн payment operation-ийн алдааг хэмжиж болно.

Бүтэн гаралт:

```text
results/chaos.txt
```

## 6. Зориуд FAIL болгосон туршилт

FAIL хувилбарыг `slo-test-fail.js` файлд тусад нь хадгалсан.

`/report` endpoint нь 200–400 ms орчим зориудын сааталтай учир дараах хатуу threshold ашигласан:

```javascript
'http_req_duration{name:report}': ['p(95)<100']
```

### FAIL туршилтын бодит үр дүн

| Үзүүлэлт | Threshold | Бодит утга | Үр дүн |
|---|---:|---:|---|
| `/report` p95 | < 100 ms | 398.35 ms | FAIL |
| Availability / checks | > 90% | 98.42% | PASS |
| `/cart/add` p95 | < 50 ms | 551.24 µs | PASS |
| `/pay` error rate | < 8% | 4.71% | PASS |

`/report` endpoint-ийн p95 latency **398.35 ms** болсон бөгөөд 100 ms-ийн босгоос өндөр байсан учир threshold зориудаар FAIL болсон.

k6 дараах алдааг гаргасан:

```text
thresholds on metrics 'http_req_duration{name:report}' have been crossed
```

PowerShell дээр шалгасан exit code:

```text
99
```

Ийм non-zero exit code нь CI/CD pipeline-д performance quality gate зөрчигдсөнийг илрүүлж build эсвэл deployment процессыг зогсоох боломж олгоно.

Бүтэн гаралт:

```text
results/fail.txt
```

## 7. Дүгнэлт

Энэхүү лабораторийн ажлаар чанарын сценариог хэмжигдэхүйц SLO болгон хувиргаж, дараа нь k6 threshold ашиглан автоматаар шалгах үйл явцыг практик дээр хэрэгжүүллээ. Хамгийн хэцүү хэсэг нь ерөнхий чанарын шаардлагыг системийн бодит зан төлөвт тохирсон тоон босго болгон тодорхойлох байсан. Performance сценариод `/cart/add` endpoint маш хурдан ажилласан бөгөөд p95 latency нь сонгосон SLO-г хангаж чадсан. Reliability сценариод `/pay` endpoint-ийн зориудын алдааны хувьтай уялдуулан 8%-ийн босго сонгосон бөгөөд хэвийн тестийн үед 3.97% гарч PASS болсон. `/report` endpoint-ийн p95 нь 392.72 ms байсан бөгөөд 450 ms-ийн performance босгыг мөн хангасан. Chaos туршилтаар серверийг зориудаар зогсооход availability 81.21% болж, 90%-ийн SLO-г хангаж чадаагүй. Мөн `/pay` error rate 21.93% болж reliability SLO зэрэг FAIL болсон нь нэг системийн эвдрэл хэд хэдэн чанарын хэмжүүрт зэрэг нөлөөлж болохыг харуулсан. 10 секундийн зогсолт нь цагаар тооцсон 12 секундийн error budget дотор байсан боловч хүсэлтээр тооцсон availability илүү ихээр муудсан. Зориудын FAIL туршилтад `/report` endpoint-д p95 < 100 ms гэсэн хатуу threshold өгөхөд бодит p95 398.35 ms гарч threshold FAIL болсон. Ийнхүү сценарио → SLO → threshold гэсэн холбоог бодит хэмжилт, chaos туршилт болон k6-ийн exit code ашиглан бүрэн шалгалаа.
